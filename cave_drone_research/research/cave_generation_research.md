## Executive Summary

This report surveys six procedural cave generation paradigms relevant to autonomous drone exploration with LiDAR SLAM. The most immediately applicable approach for robotics simulation is a **hybrid pipeline** that:

1. Uses **graph-based topology** (randomized Prim's/Kruskal's or probabilistic node placement) to define the skeleton of the cave network, guaranteeing connectivity and controlling branching factor, chamber placement, and dead ends.
2. Applies **spline sweeping or SDF blending** along graph edges to generate 3D tube geometry with organic cross-sections.
3. Adds **Perlin/Simplex noise displacement** on the SDF iso-surface to break artificial symmetry.
4. Exports via **Collada (.dae) or OBJ** for Gazebo/ROS2 ingestion, with a separate low-poly collision mesh.

The **PLUME** framework (2025, arXiv) is the closest production-ready open-source tool to this pipeline and was explicitly validated with LiDAR SLAM (RTAB-Map) in Gazebo. The **DARPA SubT** tile-based system provides the most battle-tested, competition-validated cave assets but requires manual tile composition rather than full procedural generation.

## Method 1: Graph-Based Topology Generation

### Concept

The cave network is first abstracted as a graph: nodes represent chambers or passage junctions; edges represent tunnel segments. The geometry is then generated by sweeping volumes along graph edges. Two main sub-approaches:

**1A. Randomized MST + cycle addition (Prim's / Kruskal's)**

- Begin with a set of randomly distributed nodes in 3D space.
- Use **Randomized Prim's** or **Kruskal's** to build a minimum spanning tree, guaranteeing full connectivity with no isolated regions.
- Add 1–3 extra random edges to the MST to create loops, preventing a purely tree-like structure (loops are critical for making environments non-trivial for SLAM).
- Assign tunnel radii and cross-section shapes to each edge; sweep geometry along spline-interpolated paths.

**1B. L-Systems (Lindenmayer Systems)**

- A bracketed L-system drives a 3D turtle that generates structural branch points.
- Symbols like `[`, `]`, `+`, `-`, `^`, `&` control branching angle and direction.
- Macros (`C`=curve, `H`=vertical ascent, `Q`=branching room, `T`=ascent variant) can encode cave-specific building blocks.
- Inherently tree-like; requires explicit loop connections post-generation to create cycles.
- Parameters: turtle angle, branch length scale, macro strings, volume constraints.

## Method 2: Space Colonization Algorithm

### Concept

Adapted from tree/vascular generation. A set of **attraction points** (resources) is scattered in a 3D volume. One or more **root nodes** grow branches iteratively:

1. Each attraction point finds its closest branch node within an *influence radius*.
2. Branch nodes compute a weighted average direction toward all attractors in range.
3. New nodes grow one step in that averaged direction.
4. Attractors within a *kill radius* of any node are removed.

The result is an organic branching network that naturally distributes through the space. Unlike L-systems, the final shape is driven by the distribution of attractors, not production rules.

**Cave adaptation:** Instead of growing outward from a trunk, you invert the concept — scatter attractors throughout the cave volume and grow tunnels from multiple seed points simultaneously. The shape of the attractor cloud determines the cave's extent and density.

### Key Properties

- **Branching character:** Produces smooth, organic branching with variable passage density. Very natural looking.
- **Loops:** The standard algorithm produces trees (no loops). Loops require either: (a) explicit post-connection of nearby branch tips, or (b) running multiple independent growths that merge.
- **3D chambers:** Concentrate attractors in cluster regions to naturally grow chamber-like enlargements.

### Academic Papers

- **"Modeling Trees with a Space Colonization Algorithm"**, Runions, Lane & Prusinkiewicz, 2007.  
  The foundational paper. URL: https://algorithmicbotany.org/papers/colonization.egwnp2007.pdf

- Applied to caves implicitly in PLUME's probabilistic graph generation, which shares similar attraction mechanics.

### GitHub Implementations

- **ciphrd.com space colonization (Unity/C#)**: https://ciphrd.com/articles/generating-a-3d-growing-tree-using-a-space-colonization-algorithm/ — detailed walkthrough with mesh generation from branch structure.
- **dsforza96/tree-gen (C++)**: https://github.com/dsforza96/tree-gen — parallel C++ implementation using Voronoi diagrams for spatial acceleration.

**Best for:** Generating the most organic, visually realistic cave networks, especially for visual SLAM (V-SLAM) validation where appearance diversity matters.

## Method 3: SDF / Noise + Marching Cubes

### Concept

The cave is represented as a **scalar density field** `f(x,y,z)` over a voxel grid. Cells where `f > threshold` are solid rock; cells below are empty space. The iso-surface at `f = threshold` is extracted as a mesh using **Marching Cubes**.

**Density field construction for caves:**

1. **Base solid:** Start with `f(x,y,z) = 1` (all rock).
2. **Carve tunnels:** Subtract a signed distance field along tunnel paths: `f -= max(0, r - dist_to_path(x,y,z))` where `r` is tunnel radius.
3. **Add noise:** `f += ε · Perlin3D(x·freq, y·freq, z·freq)` to roughen walls.
4. **Layer noise (fBm):** Multiple octaves of noise at different frequencies create multi-scale surface detail:

```
noise = Σ (amplitude_i · simplex3D(x·frequency_i, y·frequency_i, z·frequency_i))
```

**Key insight for caves vs. terrain:** 3D noise (not 2D heightmap noise) is required to generate overhangs, arches, and full tunnel interiors. A 2D Perlin heightmap cannot represent cave ceilings.

**SDF composition for passages:**

```
tunnel_sdf(p) = max_over_edges( r_edge - dist(p, edge_centerline) )
```

The smooth-union operator blends multiple tunnel SDFs to create seamless junctions:

```
smooth_union(a, b, k) = -log(exp(-k·a) + exp(-k·b)) / k
```

### Marching Cubes Details

- Operates on a 3D grid of voxels (e.g., 64³ to 256³).
- Each cube has 8 corners; 2⁸ = 256 configuration cases, reduced to 15 by symmetry.
- Edge intersection points interpolated between corners.
- **Mesh quality:** Naturally produces smooth, manifold meshes. The key challenge is ensuring watertightness at chunk boundaries.
- **GPU acceleration:** The algorithm is highly parallelizable; each cube is independent. GPGPU implementations achieve real-time generation.

## Method 4: Spline-Based Sweep Methods

### Concept

A cave passage is defined by a **centerline path** (Bézier spline, Catmull-Rom spline, or NURBS) and a **cross-section profile** (circle, ellipse, or irregular polygon). The 3D tunnel mesh is generated by sweeping the cross-section along the path using the Frenet-Serret frame or a more stable **parallel transport frame** (avoids rotation flipping at inflection points).

**Implementation steps:**

1. Define a spline path through 3D control points (can come from graph edges with noise perturbation).
2. Sample the spline at regular arc-length intervals.
3. At each sample point, compute the parallel transport frame (tangent + two normal vectors).
4. Place a ring of vertices at cross-section radius around the sample point, aligned with the frame.
5. Connect consecutive rings with quad strips (two triangles per quad).
6. Close end-caps and ensure watertightness.

**Variations:**
- **Variable radius:** Cross-section radius varies along the path (larger at chambers, narrower at passages). Controlled by a 1D function of arc length.
- **Cross-section deformation:** Apply noise to the cross-section polygon at each ring to break circular symmetry.
- **Branching:** At junction nodes, blend multiple swept tubes using boolean union or smooth-union SDF.

### Implementations

- **UE5 PCG + Geometry Script tutorial**: https://www.youtube.com/watch?v=n7bPNo159Hc — spline-driven procedural cave in Unreal Engine 5 using PCG graph. Spawns spheres along splines, converts to dynamic mesh.
- **Blender Geometry Nodes approach**: PLUME uses this internally — create a skin around a graph skeleton using Blender's `Skin` modifier, then apply `Subdivision Surface` and `Displace` with texture for roughness.
- **"Arches" framework** (referenced in Pytel & Mann 2015): supports sweeping passages with complicated cross-sections and placing collapsed rock. Academic tool.

### Integration with Graph Methods

Spline sweep is the preferred geometry generation step in the hybrid pipeline:

```
Graph skeleton → Edge paths → Bézier spline smoothing → 
Variable-radius sweep → Boolean union at junctions → 
SDF noise displacement → Marching Cubes / direct mesh
```

### Evaluation for Robotics/SLAM

| Criterion | Score | Notes |
|---|---|---|
| Realistic cave geometry | ★★★★☆ | Very realistic tunnel corridors; chambers need extra work |
| Computational complexity | O(N·S) where S = ring samples | Very fast — sub-second for most caves |
| Mesh quality | ★★★★★ | Excellent control over mesh density; watertight by construction |
| Controllability | ★★★★★ | Precise control of width, height, curvature at every point |
| SLAM suitability | ★★★★★ | Clean, predictable geometry; easy to ensure minimum passage widths for drone clearance |

**Best for:** When precise control of passage dimensions is required (e.g., guaranteeing a 0.5m minimum clearance for a drone of known size). Best used as the geometry step in a hybrid pipeline.

## Method 5: Cellular Automata

### Concept

A 2D or 3D grid of binary cells (0=empty/air, 1=solid/rock) evolves according to local neighborhood rules. The standard **B5678/S45678** rule (birth if ≥5 live neighbors, survival if ≥4 live neighbors) applied to a randomly seeded grid produces organic, blob-like cave shapes.

**Algorithm:**

1. Initialize grid: each cell independently set to 1 (wall) with probability `p` (typically 0.45–0.55).
2. Apply border: all boundary cells are forced to 1.
3. Iterate smoothing rule `n` times (typically 4–6):
   - For each cell, count its 8 (2D) or 26 (3D) neighbors.
   - Apply birth/survival thresholds.
4. Post-process: flood fill to identify disconnected regions → connect with carved tunnels using MST.
5. In 2D: apply marching squares to extract a smooth mesh outline, then extrude walls.
6. In 3D: directly apply marching cubes to the 3D cell grid.

**Advanced variant (constrained CA):**
Use four cell states: {definitively dead, dead, alive, definitively alive}. Pre-place "definitively alive" corridors (from a graph skeleton) as constraints, then run CA for organic fill. This hybrid approach (Vagabond method, pvigier 2019) gives controllable organic results without losing topology control.

**Float-value CA (Thijmen Bos approach):**
Instead of binary 0/1, use float values in [0,1]. The CA rule blends neighbor values → smoother output → marching cubes interpolation produces much smoother meshes than binary CA.

### 3D Extension

The 3D CA version operates on a full 3D voxel grid. Computational cost scales as O(N³) per iteration. Key challenge: 3D CA produces less visually appealing results at large scale, tends toward uniform blobs rather than passage-like structures. Typical mitigation: use CA for local wall roughness only, with graph/spline controlling the overall structure.

## Method 6: Wave Function Collapse (WFC)

### Concept

WFC is a **constraint-propagation** approach to procedural generation. A tileset of pre-designed cave modules (tunnel segments, T-junctions, corners, chambers, dead ends, etc.) is defined with explicit adjacency constraints (which tiles can be placed next to each other). The algorithm:

1. Initializes a 3D grid where every cell is in a superposition of all possible tiles.
2. Selects the cell with **lowest entropy** (fewest valid tile options).
3. **Collapses** that cell: picks one tile weighted by probability.
4. **Propagates**: removes tiles from neighbors that are now incompatible.
5. Repeats until all cells are collapsed (or a contradiction arises → backtrack).

**Key characteristics:**
- WFC operates on a discrete voxel grid; tile size directly determines passage cross-section.
- Unlike L-systems, WFC can enforce structural coherence from a design perspective (each tile is a hand-crafted 3D model).
- WFC alone is unreliable for ensuring connectivity (a required path between entrance and exit) — requires extra constraints or a hybrid approach (pre-route with MST, then WFC fills the rest).

**3D WFC for caves:**

```
Socket matching: each tile face has a "socket" type (open passage, wall, etc.)
Adjacency constraint: tile A can be placed next to tile B if their shared face sockets match
Layer-based generation: generate floor-by-floor (bottom to top) for better control
```

A 2025 Eurographics paper (Villar López & Chover) extends WFC to 3D maps with: tile weights, layer-based generation, appearance constraints for unique tiles, and automated neighbor socket creation.

**Known limitation for caves:** WFC generates locally consistent results but lacks global structure. A large WFC cave may have many dead-end pockets that don't form coherent exploration routes. The recommendation from practitioners (r/proceduralgeneration, Brian Bucklew) is to use WFC as a *decorative fill* on top of a pre-defined structural skeleton.

## Gazebo / ROS Integration and Mesh Formats

### Compatible Mesh Formats

| Format | Extension | Gazebo Support | Notes |
|--------|-----------|----------------|-------|
| COLLADA | .dae | ✅ Full (visual + collision) | Preferred format; supports materials, textures, transform hierarchies |
| OBJ + MTL | .obj | ✅ Visual; limited collision | Widely supported; no animation |
| STL | .stl | ✅ Collision; no texture | Preferred for collision meshes due to simplicity |
| PLY | .ply | ✅ Limited | Useful for point cloud exchange |
| USD/USDA | .usd | ✅ Ignition/Gazebo Garden+ | Newer format; good for complex scenes |

### Gazebo Model Structure

For a custom cave mesh in Gazebo:

```xml
<!-- model.sdf -->
<model name="cave_01">
  <static>true</static>
  <link name="cave_link">
    <visual name="visual">
      <geometry>
        <mesh>
          <uri>model://cave_01/meshes/cave_visual.dae</uri>
          <scale>1 1 1</scale>
        </mesh>
      </geometry>
    </visual>
    <collision name="collision">
      <geometry>
        <mesh>
          <!-- Use lower-poly mesh for physics performance -->
          <uri>model://cave_01/meshes/cave_collision.stl</uri>
        </mesh>
      </geometry>
    </collision>
  </link>
</model>
```

**Key rules:**
- Separate visual mesh (high-poly, textured .dae) from collision mesh (low-poly .stl) for physics performance.
- Cave meshes should be **static** (immovable); no inertia needed.
- Collision mesh must be **watertight** (no open edges) for reliable physics.
- LiDAR collision detection relies on the collision mesh, not the visual mesh.

### Blender → Gazebo Pipeline

From the Gazebo sim official documentation ([Procedural Datasets with Blender](https://gazebosim.org/api/sim/9/blender_procedural_datasets.html)):

1. Create cave in Blender with Geometry Nodes.
2. Export visual mesh: **File → Export → Collada (.dae)** or use the automated Python script.
3. Export collision mesh: decimate to ~5–10% of visual polygon count → **Export → STL**.
4. Run [Gazebo procedural dataset script](https://github.com/gazebosim/gz-sim/tree/main/examples/scripts/blender_procedural_datasets):

```bash
blender --background rock.blend \
  --python blender_dataset_exporter.py \
  -- --mesh-format dae --num-models 10 --output-dir ./models
```

Supported formats for automated export: `.dae`, `.obj`, `.stl`.

**PLUME** (https://github.com/Gabryss/P.L.U.M.E) automates this pipeline end-to-end for caves. Output formats: `obj`, `ply`, `usd`. PLUME-generated caves have been validated with Gazebo + RTAB-Map LiDAR SLAM.

### Mesh Quality for Physics Simulation

**Watertightness requirements:**
- The collision mesh must form a closed manifold (no holes, no non-manifold edges).
- Common issue: marching cubes at chunk boundaries leaves T-junctions. Fix with a post-processing weld vertices step.
- Use [Manifold](https://github.com/elalish/manifold) (C++ library) or Blender's "3D Print Toolbox" → "Make Manifold" to repair meshes.

**Triangle count guidelines for Gazebo:**
- Visual mesh: 100K–500K triangles per cave environment (acceptable for rendering).
- Collision mesh: 5K–50K triangles (critical for real-time physics). Complex collision meshes cause significant FPS drops.
- Use **convex decomposition** (V-HACD algorithm) for complex interior cave collision if performance is critical.

## Obstacles: Stalactites, Rubble, Narrow Squeezes

### Stalactites and Stalagmites

**Procedural generation approaches:**

1. **Cone/cylinder parametric shapes (Cui et al. 2011)**  
   Generate stalactites as tapered cylinders with Laplacian smoothing. Parameters: base radius `r_base`, tip radius `r_tip`, height `h`, curvature. Place at random ceiling positions with minimum spacing constraint. Variable taper produces different maturity stages.

2. **L-system stalactites**  
   Small L-systems with gravitropism (tip grows downward under gravity rule) produce branched stalactite clusters. The FDG2015 GPU paper uses a cellular automata shader to grow stalactites iteratively.

3. **Physical simulation (GPU)**  
   GPU-based calcite precipitation simulation produces geologically accurate speleothems (Modelling and Animation of Stalactite Growth, Eurographics 2024). URL: https://diglib.eg.org/items/b4a33ab2-5c35-4b0a-8bb8-f2dc7d831d0c. Computationally expensive but produces most realistic results.

4. **Asset scatter with PCG**  
   Place pre-made stalactite mesh assets procedurally using Poisson disk sampling on ceiling faces. Vary scale/rotation/type for visual diversity. This is the approach used in DARPA SubT tile environments.

**For Gazebo:** Stalactites should be modeled as separate static models (not part of the cave mesh) to allow independent collision meshes and potentially dynamic physics if rock falls are desired.

### Rubble and Rock Piles

- Scatter random convex rock meshes on floor using Poisson disk sampling on floor faces.
- Rock shapes: parametric rounded polyhedra with random scale. Alternatively: import pre-made rock meshes (Gazebo Fuel has free rock models).
- The [Gazebo Fuel rock.blend example](https://gazebosim.org/api/sim/9/blender_procedural_datasets.html) provides a randomized rock generator using Blender Geometry Nodes.
- For physics: rocks should have inertial properties set; use convex hulls for collision.

### Narrow Squeeze Points

- Identify bottleneck passages in the graph skeleton (minimum radius cross-sections).
- Explicitly carve tunnel radii to be at or below drone clearance (e.g., 0.6–0.8m for a 0.3m wingspan drone, which is 2× wingspan per side recommended for SLAM validation).
- Add random "pinch" perturbations: at random arc-length positions along a tunnel, locally reduce the SDF radius by 20–40%.
- Ensure a minimum 0.4m clearance is maintained everywhere to guarantee navigability (adjust for drone size).

## Recommended Pipeline

### Full Pipeline for Drone LiDAR SLAM Cave Simulation

```
Stage 1: TOPOLOGY (Graph-based)
  - Place N nodes in 3D bounded volume (100m × 100m × 30m)
  - Run randomized Prim's to build spanning tree (guaranteed connectivity)
  - Add K extra edges to create loops (loop closures for SLAM testing)
  - Assign: node radius (chamber size), edge radius (passage width), path curvature
  - Output: graph G = (V, E) with metadata

Stage 2: SKELETON PATHS (Spline smoothing)
  - For each edge, fit a Catmull-Rom spline through: start node → 2 intermediate control 
    points (randomly perturbed midpoints) → end node
  - Apply Perlin 3D displacement to control points (σ = 0.1 × edge_length)
  - Output: set of smooth 3D spline paths with variable radii

Stage 3: GEOMETRY GENERATION (SDF + Marching Cubes)
  - Initialize voxel grid at target resolution (e.g., 0.2m voxel = 500³ for 100m cave)
  - For each spline: carve SDF tunnel (smooth-union of spheres along path)
  - Add Simplex 3D noise to SDF: σ = 0.3 × min_radius, frequency = 0.05/m
  - Run Marching Cubes to extract iso-surface
  - Invert normals (inside of cave is the visible surface)
  - Output: raw triangle mesh

Stage 4: MESH POST-PROCESSING
  - Weld vertices at chunk seams (watertight check)
  - Fill any holes (use libigl or Blender 3D Print Toolbox)
  - Decimate to target polygon count: 200K triangles visual, 20K collision
  - Verify manifold (no open edges, no self-intersections)
  - Output: watertight high-poly visual mesh + low-poly collision mesh

Stage 5: OBSTACLE PLACEMENT
  - Stalactites: Poisson disk sample ceiling faces, place parametric cone meshes
  - Rubble: Poisson disk sample floor faces with exclusion zones around passages
  - Narrow squeezes: Applied in Stage 3 via local radius reduction on spline paths

Stage 6: EXPORT TO GAZEBO
  - Visual: export as Collada (.dae) with material/texture references
  - Collision: export as STL
  - Write model.sdf referencing both meshes
  - Test: load in Gazebo, spawn drone, run LiDAR plugin, verify ray collisions
```
